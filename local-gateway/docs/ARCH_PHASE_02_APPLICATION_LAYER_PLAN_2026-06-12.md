# 阶段 2：应用层与调用链收口计划

更新时间：2026-06-12  
阶段目标：让系统的主行为有统一入口，不再让各类调用直接撞到底层实现

## 1. 本阶段目标

本阶段要解决的核心问题是：

当前系统的业务能力被多个入口直接调用：

- HTTP router
- AI agent
- 自动化逻辑
- 邮件策略
- 前端对应接口路径

本阶段目标是为这些调用建立统一的应用层抽象。

## 2. 本阶段希望达到的结构结果

重整后，系统的调用关系应当朝以下方向演进：

```text
入口层（HTTP / AI / automation / portal）
-> application/use case 层
-> domain/service 层
-> persistence/runtime 层
```

本阶段只规划这个结构，不写具体实现代码。

## 3. 范围

包含：

- 用例层职责定义
- 主调用链识别
- 各入口与用例的映射关系
- 统一入口规范

不包含：

- 具体 use case 类或函数实现
- 现有 router/service 立即改造
- 调用链实装切换

## 4. 待完成任务

### 任务 A：定义 application/use case 层职责

需要明确：

- 什么属于用例层
- 什么不属于用例层

用例层负责：

- 组织一个完整业务动作
- 协调多个模块
- 控制事务边界与调用顺序
- 暴露给不同入口复用

用例层不负责：

- HTTP 参数解析
- 页面状态管理
- 底层 SQL 或 JSON 文件操作细节
- 大量工具函数堆叠

### 任务 B：梳理主用例清单

至少梳理以下主用例族：

#### productivity

- 创建任务
- 更新任务
- 完成任务
- 批量规划任务
- 查询今日面板
- 创建任务关联笔记

#### agent

- 发起对话
- 运行工具调用
- 保存对话记录
- 预览计划
- 确认计划
- 重排计划

#### mail

- 创建账户
- 拉取邮件线程
- 创建草稿
- 发送草稿
- 生成回信草稿
- 从邮件创建任务
- 运行自动回信策略

#### platform

- 同步变更
- 发送通知
- 触发 webhook
- 运行 workflow

### 任务 C：梳理入口到用例的映射关系

要明确：

- 哪些 router 对应哪些用例
- 哪些 AI tool call 对应哪些用例
- 哪些自动化行为调用哪些用例
- 哪些 portal 行为对应哪些用例

### 任务 D：识别“通过 HTTP 回打自身”的路径

需要列出当前这类路径，并标记为后续重点收口对象。

这类路径通常意味着：

- 内部调用被表层协议绑住
- 领域能力没有稳定内部入口

### 任务 E：定义统一调用原则

建议明确以下原则：

1. HTTP 只调用 application/use case
2. AI 不直接调用 router HTTP 语义
3. 自动化不直接深入多个底层 service 细节
4. 跨模块动作必须通过明确用例组织

## 5. 依赖关系

本阶段依赖：

- 阶段 1 的模块边界与归属结果

本阶段输出将影响：

- 阶段 3 的状态治理
- 阶段 5 的兼容层收缩

## 6. 风险与阻塞点

### 风险 1：把用例层做成另一层 service 堆

如果只是复制一层名字，没有真正承担调用组织职责，就没有意义。

### 风险 2：跨模块用例定义不清

例如“从邮件创建任务”，如果没有明确定义，就会继续散落在 mail/task 两边。

### 风险 3：想一步切换所有调用链

本阶段只做规划，不追求立刻替换全部入口。

## 7. 产出物

本阶段产出应包括：

1. application/use case 层职责说明
2. 主用例清单
3. 入口到用例映射表
4. 需收口的内部 HTTP 回打路径清单
5. 统一调用原则清单

## 8. 完成标准

满足以下条件，才算本阶段完成：

1. 核心业务动作已经可以被描述成明确用例
2. 每个主要入口都能映射到用例层
3. 跨模块动作不再被视为“谁方便谁做”
4. 后续代码改造已经有明确收口方向

## 9. 本阶段不做的事情

本阶段明确不做：

- 真正新建全部 use case 文件
- 替换所有 router 调用
- 重写 AI tool dispatch
- 大规模删旧 service
