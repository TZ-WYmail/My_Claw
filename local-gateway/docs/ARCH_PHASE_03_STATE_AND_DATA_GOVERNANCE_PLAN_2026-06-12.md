# 阶段 3：状态模型与数据所有权治理计划

更新时间：2026-06-12  
阶段目标：让系统知道“什么状态属于谁，应该存在哪，为什么这样存”

## 1. 本阶段目标

当前系统同时使用：

- SQLite
- JSON 配置文件
- JSONL 历史文件
- 内存队列/任务状态
- scheduler 运行时状态

本阶段目标是建立统一状态模型，而不是继续按便利性分散存储。

## 2. 本阶段核心问题

本阶段要回答以下问题：

1. 哪些状态是主业务数据
2. 哪些状态是运行时临时数据
3. 哪些状态是缓存
4. 哪些状态是审计与历史记录
5. 哪些状态允许丢失
6. 哪些状态必须有明确所有者

## 3. 范围

包含：

- 数据分类
- 状态分类
- 所有权定义
- 生命周期定义
- 迁移优先级排序

不包含：

- 实际数据库迁移
- 实际 JSON 到 DB 的转换
- 持久化层代码重写

## 4. 待完成任务

### 任务 A：建立状态分类表

建议至少分为：

1. 主业务状态
2. 配置状态
3. 运行时状态
4. 缓存状态
5. 审计状态
6. 会话状态

### 任务 B：盘点现有状态载体

需要列出当前存在的主要状态载体，例如：

- `tasks.db`
- `ai_config.json`
- `conversations/*.jsonl`
- `sync_state.json`
- 内存 `_jobs`
- 调度器内部状态

### 任务 C：为每类状态定义所有权

必须明确：

- 哪个模块拥有该状态
- 谁可以写
- 谁可以读
- 谁只能通过正式接口访问

### 任务 D：定义生命周期与可靠性等级

每类状态都要回答：

- 服务重启后是否必须保留
- 系统异常后是否允许丢
- 是否需要审计追溯
- 是否需要版本化

### 任务 E：识别高风险混合状态

重点识别：

- 被多个模块直接读写的状态
- 既承担配置又承担运行时职责的状态
- 既是审计记录又被用作主数据来源的状态

### 任务 F：建立治理原则

建议明确以下原则：

1. 主业务数据必须有明确模块所有权
2. 运行时临时态不应被误当持久主数据
3. 审计日志不应承担业务主读取职责
4. 配置状态与会话状态不能混放
5. 内存状态必须标明丢失后果

## 5. 依赖关系

本阶段依赖：

- 阶段 1 的模块边界
- 阶段 2 的应用层调用关系

本阶段输出将影响：

- 后续持久化重构
- 兼容层清理
- 前端状态对接方式

## 6. 风险与阻塞点

### 风险 1：状态分类标准不一致

如果没有先定标准，最后只能变成另一个文件清单。

### 风险 2：历史兼容数据阻碍判断

旧路径保留下来的数据形式容易掩盖真实主路径。

### 风险 3：把所有状态都往数据库里塞

本阶段不是为了“一切入库”，而是为了让存储决策可解释。

## 7. 产出物

本阶段产出应包括：

1. 状态分类矩阵
2. 状态载体盘点表
3. 状态所有权清单
4. 生命周期与可靠性等级表
5. 高风险混合状态清单
6. 状态治理原则清单

## 8. 完成标准

满足以下条件，才算本阶段完成：

1. 每种重要状态都有类别和所有者
2. 多模块共享状态已被识别
3. 运行时状态与持久状态已被明确区分
4. 后续迁移优先级已经可排序

## 9. 本阶段不做的事情

本阶段明确不做：

- 直接迁移数据库
- 删除 JSON/JSONL 文件机制
- 重写 conversation 存储
- 替换下载/任务/同步状态实现
