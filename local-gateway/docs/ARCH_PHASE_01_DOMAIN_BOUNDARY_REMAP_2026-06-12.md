# 阶段 1：领域边界与模块版图重建计划

更新时间：2026-06-12  
阶段目标：把现有代码从“按技术层堆放”重新映射到“按领域理解”

## 1. 本阶段目标

本阶段的目标不是改目录，而是先完成下面两件事：

1. 建立新的模块版图
2. 把现有文件和能力映射到版图中

也就是说，本阶段要回答：

- 现有代码分别属于哪个模块
- 哪些文件边界清晰
- 哪些文件跨了多个模块
- 哪些模块之间当前耦合最严重

## 2. 范围

包含：

- 一级模块细化
- 二级子域划分
- 当前文件归属映射
- 跨域文件识别
- 越界关系识别

不包含：

- 实际移动文件
- service 拆分落地
- API 改名
- 前端组件迁移

## 3. 模块草案

建议先采用以下一级模块：

### 模块 A：productivity

负责：

- task
- note
- habit
- pomodoro
- calendar
- dashboard 中偏个人工作流的部分

### 模块 B：agent

负责：

- chat runtime
- ai planning
- tool orchestration
- conversation state

### 模块 C：mail

负责：

- account
- thread
- message
- draft
- polling
- mail automation
- portal

### 模块 D：platform

负责：

- sync
- encryption
- webhook
- workflow
- shortcut
- mobile integration
- voice
- notification
- sandbox/download/search 等系统能力

## 4. 待完成任务

### 任务 A：建立文件归属清单

为现有关键目录建立映射表：

- `routers/*`
- `services/*`
- `services/mail/*`
- `frontend/src/pages/*`
- `frontend/src/components/*`
- `frontend/src/hooks/*`

输出要求：

- 每个文件至少有一个主归属模块
- 如果存在副归属，也要标注

### 任务 B：识别跨域中枢文件

重点识别以下类型文件：

- 既管业务又管统计
- 既管运行时又管持久化
- 既管主路径又管兼容层
- 既管多个子域又缺少清晰边界

目标是列出高风险中枢文件清单。

### 任务 C：识别越界依赖

需要列出：

- 哪些模块当前直接调用了别的模块内部细节
- 哪些模块绕过了对方的正式入口
- 哪些模块之间存在双向耦合

### 任务 D：定义每个模块的对外入口

为每个一级模块定义：

- 对外暴露什么能力
- 通过什么入口暴露
- 哪些能力不能被直接跨域调用

### 任务 E：识别兼容层

要明确列出：

- 哪些文件主要是兼容旧命名
- 哪些文件主要是兼容旧调用方式
- 哪些文件是临时聚合层

## 5. 依赖关系

本阶段依赖：

- 阶段 0 的模块语言统一结果

本阶段的输出将直接供以下阶段使用：

- 阶段 2 的应用层收口
- 阶段 4 的前端对齐
- 阶段 5 的兼容层收缩

## 6. 风险与阻塞点

### 风险 1：文件归属无法单一确定

这不是失败信号，恰恰说明它是重构热点。

### 风险 2：把技术能力误当业务模块

例如 download/search/sandbox，到底属于 product 还是 platform，需要先统一标准。

### 风险 3：邮件和 productivity 之间职责缠绕

例如“从邮件创建任务”这种跨域流程，必须明确它是跨域用例，不是模块归属混合。

## 7. 产出物

本阶段产出应包括：

1. 一级模块定义表
2. 二级子域草案
3. 文件归属映射表
4. 跨域中枢文件清单
5. 越界依赖清单
6. 兼容层识别清单

## 8. 完成标准

满足以下条件，才算本阶段完成：

1. 主要文件都能归属到模块
2. 高风险跨域文件已被识别
3. 核心模块的对外入口已经定义
4. 后续拆分不再需要从零猜边界

## 9. 本阶段不做的事情

本阶段明确不做：

- 文件迁移
- 目录重命名
- 函数重写
- service 拆类
- 页面拆组件
