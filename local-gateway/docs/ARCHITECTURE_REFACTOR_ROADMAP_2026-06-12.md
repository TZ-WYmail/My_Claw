# LocalCommandCenter 架构重整路线图

更新时间：2026-06-12  
定位：这是架构与设计层的重整路线图，不涉及具体代码实现方案  
目标：把当前“功能堆叠式增长”的应用，收敛为“边界明确的模块化单体”

## 1. 路线图目标

本轮 planning 不追求一次性重写项目，而是追求以下 5 个结果：

1. 明确系统产品身份与一级模块边界
2. 明确主调用路径，避免继续通过 HTTP 回打自身 API
3. 明确数据与运行时状态所有权
4. 明确前端页面、命名和真实业务的对应关系
5. 在不破坏现有能力的前提下，为后续渐进重构提供顺序和停靠点

## 2. 设计原则

本轮所有阶段都遵守以下原则：

1. 先改认知与边界，不先改实现细节
2. 先收口主路径，再处理兼容层
3. 先稳定模块职责，再决定目录形态
4. 先定义数据所有权，再谈持久化重构
5. 每一阶段都必须有可验证产出

## 3. 阶段划分

本轮重整分为 6 个阶段：

### 阶段 0：架构认知统一

目标：

- 统一系统定位
- 统一一级模块划分
- 统一主路径、兼容路径、遗留路径定义

文档：

- `ARCH_PHASE_00_ARCHITECTURE_ALIGNMENT_2026-06-12.md`

### 阶段 1：领域边界与模块版图重建

目标：

- 把当前代码映射到新的领域边界
- 标记每个模块的职责、边界、对外能力与禁止越界点

文档：

- `ARCH_PHASE_01_DOMAIN_BOUNDARY_REMAP_2026-06-12.md`

### 阶段 2：应用层与调用链收口

目标：

- 建立 application/use-case 层的设计规则
- 收口 HTTP、AI、自动化、前端背后的统一用例入口

文档：

- `ARCH_PHASE_02_APPLICATION_LAYER_PLAN_2026-06-12.md`

### 阶段 3：状态模型与数据所有权治理

目标：

- 明确数据库、JSON、JSONL、内存状态、调度器状态的归属
- 明确什么是持久状态、临时状态、缓存状态、审计状态

文档：

- `ARCH_PHASE_03_STATE_AND_DATA_GOVERNANCE_PLAN_2026-06-12.md`

### 阶段 4：前端信息架构与命名对齐

目标：

- 把页面命名、业务语义、导航结构重新对齐
- 让前端的 feature boundary 和后端模块边界尽量一致

文档：

- `ARCH_PHASE_04_FRONTEND_ALIGNMENT_PLAN_2026-06-12.md`

### 阶段 5：兼容层收缩与落地验证

目标：

- 标记并收缩兼容层
- 规划回归验证、发布顺序和风险控制

文档：

- `ARCH_PHASE_05_COMPATIBILITY_AND_VALIDATION_PLAN_2026-06-12.md`

## 4. 推荐执行顺序

严格按以下顺序推进：

1. 阶段 0
2. 阶段 1
3. 阶段 2
4. 阶段 3
5. 阶段 4
6. 阶段 5

不建议跳阶段，原因如下：

- 跳过阶段 0，会导致后面每个人对“系统是什么”理解不同
- 跳过阶段 1，阶段 2 的调用收口没有边界基础
- 跳过阶段 2，阶段 3 只能继续围绕旧调用链治理状态
- 跳过阶段 3，阶段 4 会继续在前端拼接不稳定状态
- 跳过阶段 5，兼容层会无限期滞留

## 5. 每阶段统一输出要求

每个阶段都必须输出：

1. 本阶段目标
2. 范围边界
3. 待完成任务清单
4. 依赖关系
5. 风险与阻塞点
6. 阶段产出物
7. 完成标准
8. 明确不在本阶段做的事情

## 6. 时间建议

这是建议节奏，不是强制排期：

- 阶段 0：1-2 天
- 阶段 1：2-4 天
- 阶段 2：3-5 天
- 阶段 3：3-5 天
- 阶段 4：2-4 天
- 阶段 5：2-3 天

合计建议跨度：

- 2 到 4 周

## 7. 成功标准

本轮架构重整 planning 完成后，应该达到以下效果：

1. 团队对系统定位有统一表述
2. 每个核心文件都能归属到明确模块
3. 新功能进入系统时有明确落点
4. AI、HTTP、自动化不再被视为各自独立的业务入口
5. 前后端命名与业务语义不再大面积失配
6. 后续代码重构可以按阶段逐步落地，而不是整体推倒

## 8. 本路线图不做的事情

本路线图明确不直接处理：

1. 具体代码迁移细节
2. 具体类、函数、目录的重命名脚本
3. 数据迁移脚本编写
4. 前端组件重写方案
5. 单个 bug 修复清单

这些属于后续执行文档或实施任务，不属于本轮 planning 的输出。
