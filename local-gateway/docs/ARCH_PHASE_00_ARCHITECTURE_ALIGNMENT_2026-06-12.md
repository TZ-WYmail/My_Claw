# 阶段 0：架构认知统一计划

更新时间：2026-06-12  
阶段目标：先统一“这个系统是什么”，再进入结构调整

## 1. 本阶段目标

本阶段只做一件事：

把当前项目从“大家各自理解中的系统”收敛成“有统一架构语言的系统”。

本阶段结束后，团队必须能对以下问题给出统一答案：

1. 这个项目的产品身份是什么
2. 它的一级模块有哪些
3. 哪些能力是核心域，哪些是平台域
4. 哪些路径是当前主路径，哪些只是兼容路径
5. 后续重构是为了什么，不是为了什么

## 2. 范围

本阶段只覆盖认知、命名、模块语言与决策对齐，不做代码改动设计。

包含：

- 产品定位统一
- 模块语言统一
- 主路径定义
- 兼容路径定义
- 重构目标与非目标统一

不包含：

- 目录迁移
- service 拆分
- 接口改造
- 数据结构调整
- 前端页面迁移

## 3. 待完成任务

### 任务 A：确认产品身份

明确系统不再仅被内部视为“local gateway”，而是：

- 一个本地优先的个人工作操作系统
- 其中网关能力只是接入层的一部分

需要完成的事情：

- 给出系统的一句话定义
- 给出不超过三句话的对外描述
- 给出一份内部统一用语表

### 任务 B：确认一级模块

明确一级模块建议至少包括：

- productivity
- agent
- mail
- platform

需要完成的事情：

- 为每个一级模块写职责说明
- 为每个一级模块列出典型功能
- 为每个一级模块列出不应承担的职责

### 任务 C：确认主路径

明确当前系统运行中的主路径：

- 后端 HTTP 主路径
- AI 调用主路径
- 邮件主路径
- 前端主路径

需要完成的事情：

- 标注主路径是什么
- 标注主路径为什么是主路径
- 标注哪些旧路径只是兼容保留

### 任务 D：确认非目标

需要把以下事情明确排除出本轮架构重整的目标：

- 全量重写
- 一次性切库
- 一次性重做前端
- 先改代码再想边界

### 任务 E：产出架构决议记录

形成正式文档或决议记录，作为后续所有阶段的前置依据。

## 4. 依赖关系

本阶段依赖：

- 现有项目结构梳理结果
- 当前模块职责分析结果

本阶段不依赖：

- 代码实现细节确认
- 数据迁移方案

## 5. 风险与阻塞点

### 风险 1：产品身份说法不统一

如果仍然有人把它看作“下载器 + 任务器 + AI 功能集合”，后续边界一定继续漂移。

### 风险 2：模块定义过粗或过细

- 过粗：所有东西继续堆在一起
- 过细：过早拆成伪微服务心智

### 风险 3：兼容路径被误当主路径

如果不先标明兼容层，后续设计会继续围绕历史结构打补丁。

## 6. 产出物

本阶段产出应包括：

1. 系统一句话定位
2. 一级模块定义表
3. 主路径/兼容路径清单
4. 本轮重构的目标与非目标清单
5. 一份统一术语表

## 7. 完成标准

满足以下条件，才算本阶段完成：

1. 团队对系统定位表述一致
2. 一级模块划分不再存在重大歧义
3. 后续任何文件都能尝试归属到一级模块
4. 兼容路径和主路径已被明确区分
5. 本轮重整的边界已经写清楚

## 8. 本阶段不做的事情

本阶段明确不做：

- 修改代码目录
- 新建 use case 层
- 调整数据库结构
- 改造前端路由
- 重写文档站或 README
